# Native updater: signing keys and release publishing

This guide explains first-time Ed25519 key setup, secure backups, and publishing signed updates for the native updater.

These steps are for the **developer publishing releases**, not people installing the app. End users do not need Sparkle, signing tools, or private keys.

## Sparkle compatibility

The native updater reads a **Sparkle-format RSS appcast** and verifies Ed25519 signatures produced by Sparkle's publishing tools. It implements the fields and behaviors it needs, not every Sparkle feature.

The application uses Foundation, CryptoKit, and Security without a Sparkle runtime dependency. You can still use Sparkle's standalone tools on the publishing Mac.

**Existing projects should keep their existing Ed25519 key pair.** Removing Sparkle from the app does not invalidate keys generated by Sparkle's `generate_keys` tool.

## What goes where?

| Value | Location | Purpose |
| --- | --- | --- |
| Public key | `ATHUpdatePublicEDKey` in the app's `Info.plist` | Verifies downloaded updates |
| Private key | Publisher's Keychain, with a secure backup | Signs release downloads |
| Download signature | `sparkle:edSignature` on the appcast enclosure | Authenticates one specific DMG |
| Feed URL | `ATHUpdateFeedURL` in the app's `Info.plist` | Locates the appcast |

**Do not put the public key in the appcast.** The appcast contains a signature for each download, not its verification key. The public key is safe to distribute; the private key must remain secret.

## 1. Generate keys on a clean Mac

For a genuinely new project with no existing release-signing key:

1. Download the package `sign_update.zip` from the repo, it contains the 2 required tools from the Sparkle official binary distribution
2. Extract it outside the source repository. Its directory contains `generate_keys` and `sign_update`
3. Open Terminal in that extracted directory and run:

```sh
   ./bin/generate_keys
```

4. Allow Keychain access when requested. On a fresh setup, the tool generates an Ed25519 key pair, stores the private key in your login Keychain, and prints the public key
5. Copy the public key into `ATHUpdatePublicEDKey` in the app's `Info.plist`. In this checkout, that file is `Xcode-project/About This Hack/Info.plist`
6. Set `ATHUpdateFeedURL` to the intended HTTPS appcast URL, subject to the URL restrictions described below
7. Build the app with these settings before distributing its first release.

Sparkle's output refers to `SUPublicEDKey`. **Use `ATHUpdatePublicEDKey` instead for this native updater.** Its value is the same Base64-encoded public key, not a file path or certificate.

Generate the pair once, not for each build or release. Running `generate_keys` again normally reuses the existing key in its default Keychain account rather than replacing it.

If keys already exist for another project or organization, do not delete them to obtain a new pair. Check both tools, and use the same selected account for generation, export, import, and signing. The commands here assume the default account on a clean publishing Mac.

## 2. Back up the private key

Back up the key immediately, before relying on it for published releases.

The following commands run from the extracted directory. Replace the example backup path with a location on secure, encrypted storage outside the repository; its parent directory must already exist.

```sh
umask 077
./generate_keys -x "private-key.txt"
```

The exported file is a **secret**, not an encrypted backup by itself. Keep it on encrypted storage, with access limited to authorized release maintainers. Preserve a protected backup independent of the publishing Mac.

Never put the private key or its export in:

- Git, including private repositories
- The app bundle or `Info.plist`.
- The appcast or a release attachment.
- Documentation, screenshots, logs, or support messages.

On a replacement publishing Mac, install the publishing tools and import the same backup:

```sh
./generate_keys -f "private-key.txt"
./generate_keys -p
```

The second command prints the public key. Confirm that it matches the app's `ATHUpdatePublicEDKey`. If import reports a conflicting existing key, stop and identify the correct Keychain account rather than deleting another project's key.

**A public key cannot recover a lost private key.** Losing the private key prevents signing further updates that existing installations will trust.

## 3. Sign each finished release

For every release:

1. Increase `CFBundleVersion` (the build number) and set `CFBundleShortVersionString` (the display version)
2. Build and code-sign the app
3. Finish notarization, stapling, packaging, and all other operations that modify the distributed DMG
4. Sign the **final DMG**, using the publishing account whose Keychain contains the private key:

   ```sh
   ./sign_update "/absolute/path/to/About.This.Hack.VERSION.dmg"
   ```

   Replace the example path and `VERSION` with the actual release file.

5. Copy the tool's `sparkle:edSignature` and `length` output into that release's appcast enclosure
6. Upload that exact DMG, then publish the updated appcast once the download is available.

**Do not modify, repackage, or recreate the DMG after signing it.** The signature covers its exact bytes. Any byte change requires signing again and updating the appcast signature and length.

The native updater verifies those bytes with CryptoKit's `Curve25519.Signing.PublicKey`, which implements Ed25519 and accepts the signatures produced by Sparkle's tools.

## 4. Populate the appcast

Retain the Sparkle-style RSS structure and namespace:

`xmlns:sparkle="http://www.andymatuschak.org/xml-namespaces/sparkle"`

Each release item needs:

| Field | Required value |
| --- | --- |
| `sparkle:version` | The app's `CFBundleVersion` |
| `sparkle:shortVersionString` | The app's `CFBundleShortVersionString` |
| `sparkle:minimumSystemVersion` | Minimum supported macOS version |
| Enclosure `url` | HTTPS URL of the final DMG |
| Enclosure `length` | Exact DMG byte count from `sign_update` |
| Enclosure `sparkle:edSignature` | Base64 signature from `sign_update` |

Use the existing appcast as the structural reference, but obtain a **new signature and length for every new DMG**. The appcast's build and display version must match the app inside the DMG.

This repository builds **About This Hack.app**. The updater accepts `About.This.Hack.VERSION.dmg` and `About.This.Hack-glass.VERSION.dmg` assets from `perez987/About-This-Hack` releases, and expects `About This Hack.app` or `About This Hack-glass.app` at the mounted DMG's root. The app reads its installed version and build from the bundle; they are not hard-coded in `UpdateController.swift`. 

Keep the current public key and its matching private key when publishing updates for existing installations. The native updater trusts one embedded public key and has no implemented key-rotation mechanism. Simply replacing the key pair would leave older installations unable to verify newly signed downloads.

For a genuinely new project, generate its own key pair. The implementation currently restricts the feed, GitHub repository, and DMG naming pattern. **Changing `ATHUpdateFeedURL` alone is insufficient.** Preserve equivalent restrictions for the new project's release channel.

## 6. Ed25519 signing is not Apple code signing

The checks serve different purposes:

- **Ed25519 signature:** proves that the downloaded DMG was signed using the release-signing private key corresponding to the app's embedded public key.
- **Apple code signature:** the replacement app must satisfy the installed app's code-signing requirement and bundle identity.
- **Notarization and Gatekeeper:** remain part of macOS distribution protections; the updater does not disable them.

A valid Ed25519 signature does not replace Apple code signing or notarization. Unsigned development builds cannot self-update. Test the complete flow with a signed, older build installed on a writable local volume, normally Applications, rather than running from a DMG or App Translocation.
